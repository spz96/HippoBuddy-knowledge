## Codex（过程说明）

我先沿着“会话 ID 如何生成/传递、历史消息存在哪里、每轮请求怎样回填上下文”这三条链路检查项目，然后把完整调用流程和关键代码位置串起来。

## Codex（过程说明）

已经确认项目不是把“上下文”交给浏览器临时拼接，而是以后端 `sessionId → Conversation` 为核心：活跃会话保留内存消息列表，同时把消息转录落盘。接下来我会核对发送接口、恢复接口和真正调用模型时传入的消息范围。

## Codex（过程说明）

调用链已基本串通：每一轮用户消息都是一个独立的 HTTP/SSE 请求，但请求体始终带当前 `sessionId`；服务端用它命中同一个 `Conversation`，追加本轮消息后，把该会话已有上下文再次整体送给模型。因此“同会话多轮”不是靠 HTTP 连接常驻，而是靠稳定会话键和服务端状态续接。还差最后核对长上下文压缩与重启恢复边界。

## Codex（最终回答）

该项目实现“同一个会话多轮请求”的核心是：

> 每轮都是独立的 HTTP 请求，但携带相同 `sessionId`；后端通过 `sessionId` 找回同一个 `Conversation`，并把历史消息一起发送给模型。

具体流程如下。

1. 新建会话时，前端生成 `web-${Date.now()}` 形式的 ID，并把当前会话 ID 保存到 `localStorage`。[appStore.ts](../frontend/src/stores/appStore.ts:366)

2. 用户每次发送消息，前端都从 `currentSessionId` 取出同一个 ID，放进请求体：

```json
{
  "sessionId": "web-1787800000000",
  "message": "我刚才说了什么？"
}
```

对应代码在 [chatStore.ts](../frontend/src/stores/chatStore.ts:654)。

3. 后端 `/api/chat` 解析 `sessionId`，然后调用：

```java
Conversation conversation =
    sessionManager.getOrCreateConversation(sessionId, systemPromptOverride);
```

见 [ChatApiHandler.java](../src/main/java/com/example/agent/web/handler/ChatApiHandler.java:197)。

4. `WebSessionManager` 内部维护：

```java
Map<String, Conversation> sessions = new ConcurrentHashMap<>();
```

相同 `sessionId` 会直接返回同一个 `Conversation` 实例，因此之前的 `user`、`assistant`、`tool` 消息都还在内存中。[WebSessionManager.java](../src/main/java/com/example/agent/web/session/WebSessionManager.java:233)

5. 后端先把本轮用户消息追加到会话，再获取完整的有效上下文：

```java
conversation.addMessage(userMessage);

List<Message> messages =
    conversationService.getContextForInference(conversation);
```

最终把 `messages` 整体传给模型，而不只是发送最新问题。[ConversationService.java](../src/main/java/com/example/agent/application/ConversationService.java:485) [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:226)

因此第二轮模型实际看到的内容类似：

```text
system: 你是一个编程助手
user: 我叫小明
assistant: 你好，小明
user: 我叫什么？
```

6. 模型响应后，`assistant` 消息以及工具调用结果也会继续追加到同一个 `Conversation`，供下一轮使用。[WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:434)

7. 每条消息还会异步写入：

```text
.hippo/sessions/{日期}/{sessionId}/conversation.jsonl
```

路径定义在 [WorkspaceManager.java](../src/main/java/com/example/agent/logging/WorkspaceManager.java:103)。应用重启后，`TranscriptLoader` 会加载 JSONL，重新构建 `Conversation`；长会话存在会话摘要时，则恢复为“早期摘要 + 最近消息”。[ConversationService.java](../src/main/java/com/example/agent/application/ConversationService.java:597)

另外还有两种“多轮”需要区分：

- 用户多轮：多次 `POST /api/chat`，使用相同 `sessionId`。
- Agent 内部多轮：一次用户请求中，如果模型调用工具，会形成“模型 → 工具结果 → 再次调用模型”的循环，最多 50 轮。[WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:210)

需要注意，同一会话正常情况下会通过前端 `isSending` 和后端会话锁避免并发。不过后端锁等待超过 30 秒后会删除旧锁并创建新锁，如果第一个请求仍在执行，存在两个请求同时修改同一 `Conversation` 的潜在竞态。[WebSessionManager.java](../src/main/java/com/example/agent/web/session/WebSessionManager.java:190)

## Codex（最终回答）

更完整地说，这个项目采用的是“有状态后端会话”方案：

- HTTP/SSE 连接是短暂的，每轮结束都会关闭。
- `sessionId` 是会话身份。
- `Conversation` 保存当前会话上下文。
- 每次调用模型时重新发送该会话的有效历史。
- `conversation.jsonl` 负责跨进程重启恢复。

## 一次完整的两轮对话

假设前端生成会话：

```text
sessionId = web-1787800000000
```

第一轮请求：

```http
POST /api/chat
Content-Type: application/json

{
  "sessionId": "web-1787800000000",
  "message": "我叫小明"
}
```

后端创建的会话上下文是：

```text
system: 你是一个编程助手
user: 我叫小明
```

模型回答后，继续追加：

```text
system: 你是一个编程助手
user: 我叫小明
assistant: 你好，小明
```

第二轮请求仍然使用相同 ID：

```http
POST /api/chat
Content-Type: application/json

{
  "sessionId": "web-1787800000000",
  "message": "我叫什么名字？"
}
```

后端不会创建新上下文，而是找到原来的 `Conversation`，追加第二轮用户消息：

```text
system: 你是一个编程助手
user: 我叫小明
assistant: 你好，小明
user: 我叫什么名字？
```

然后把以上消息重新发送给模型，所以模型可以回答“小明”。

也就是说，模型并没有自动记住上一次 HTTP 请求；是 HippoBuddy 在第二次请求中重新附带了历史上下文。

## 1. 前端如何保持同一个 sessionId

创建新会话时：

```typescript
createNewSession: () => {
  const id = `web-${Date.now()}`;
  set({ currentSessionId: id });
  persistCurrentSession(id);
  return id;
}
```

代码位置：[appStore.ts](../frontend/src/stores/appStore.ts:366)

当前会话 ID 还会写入：

```text
localStorage["hippo-current-session"]
```

因此页面刷新后，前端仍能知道用户之前打开的是哪个会话。[appStore.ts](../frontend/src/stores/appStore.ts:88)

每次发送消息时，前端读取当前会话：

```typescript
const { currentSessionId: sid, mode } = useAppStore.getState();
```

然后构造请求：

```typescript
const request: ChatRequest = {
  sessionId: sid,
  message,
  mode: options?.mode ?? mode,
  images: options?.images,
  selectedRules: options?.selectedRules,
};
```

见 [chatStore.ts](../frontend/src/stores/chatStore.ts:615)。

请求最终发送到：

```typescript
streamSse('/api/chat', request, onEvent, signal)
```

见 [client.ts](../frontend/src/api/client.ts:135)。

这里 SSE 只负责模型回答的流式返回，不负责保存会话。下一轮会创建一条新的 HTTP/SSE 连接。

## 2. 后端如何识别会话

`ChatApiHandler` 从请求 JSON 中读取 ID：

```java
sessionId = json.has("sessionId")
    ? json.get("sessionId").asText()
    : json.has("session")
        ? json.get("session").asText()
        : "default";
```

见 [ChatApiHandler.java](../src/main/java/com/example/agent/web/handler/ChatApiHandler.java:91)。

然后使用这个 ID 获取会话：

```java
Conversation conversation =
    sessionManager.getOrCreateConversation(
        sessionId,
        systemPromptOverride
    );
```

见 [ChatApiHandler.java](../src/main/java/com/example/agent/web/handler/ChatApiHandler.java:197)。

所以真正决定是不是“同一个会话”的，不是 Cookie、HTTP Session 或 SSE 连接，而是请求体里的 `sessionId`。

## 3. Conversation 如何在内存中保存

`WebSessionManager` 内部有一个全局并发 Map：

```java
private static final Map<String, Conversation> sessions =
    new ConcurrentHashMap<>();
```

见 [WebSessionManager.java](../src/main/java/com/example/agent/web/session/WebSessionManager.java:34)。

结构相当于：

```text
sessions
├── web-1787800000000 -> Conversation A
├── web-1787800001000 -> Conversation B
└── web-1787800002000 -> Conversation C
```

相同 `sessionId`：

```java
Conversation existing = sessions.get(sessionId);

if (existing != null) {
    return existing;
}
```

会返回同一个对象，而不是复制一个新的会话。[WebSessionManager.java](../src/main/java/com/example/agent/web/session/WebSessionManager.java:233)

如果不存在，则创建：

```java
Conversation conversation =
    conversationService.create(systemPrompt, maxTokens, id);
```

随后放入 `sessions`。[WebSessionManager.java](../src/main/java/com/example/agent/web/session/WebSessionManager.java:291)

## 4. Conversation 内部保存了什么

`Conversation` 内部核心对象是：

```java
private final ContextWindow contextWindow;
private final String sessionId;
```

见 [Conversation.java](../src/main/java/com/example/agent/domain/conversation/Conversation.java:13)。

每次添加消息：

```java
public void addMessage(Message message) {
    contextWindow.addMessage(message);
}
```

`ContextWindow` 内部维护：

```java
private final List<Message> messages;
```

消息顺序类似：

```text
Message(role=system)
Message(role=user)
Message(role=assistant)
Message(role=assistant, toolCalls=...)
Message(role=tool)
Message(role=assistant)
Message(role=user)
```

所以它不仅保存普通用户和助手消息，还保存工具调用及工具结果。这对 Agent 连续执行尤其重要。

## 5. 当前用户消息如何进入会话

普通文本消息走：

```java
Message userMsg =
    conversationService.addUserMessage(
        conversation,
        userMessage
    );
```

见 [ChatApiHandler.java](../src/main/java/com/example/agent/web/handler/ChatApiHandler.java:227)。

`ConversationService` 创建 `user` 消息并添加：

```java
public Message addUserMessage(
    Conversation conversation,
    String content
) {
    Message message = Message.user(content);
    addMessage(conversation, message);
    return message;
}
```

真正添加时同时执行三件事：

```java
conversation.addMessage(message);        // 内存上下文
memoryExtractor.onMessageAdded(...);     // 记忆提取
transcript.appendUserMessage(message);   // JSONL 持久化
```

见 [ConversationService.java](../src/main/java/com/example/agent/application/ConversationService.java:485)。

因此一条用户消息同时进入：

```text
用户消息
   ├── Conversation 内存历史
   ├── Session Memory/长期记忆处理
   └── conversation.jsonl 持久化
```

## 6. 调用模型时传递哪些历史

Agent 每次调用模型前执行：

```java
List<Message> messages =
    new ArrayList<>(
        conversationService
            .getContextForInference(conversation)
    );
```

见 [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:226)。

调用链是：

```java
getContextForInference()
    -> prepareForInference()
    -> conversation.getEffectiveMessages()
    -> memoryRetriever.prepareContextHeader()
```

见 [ConversationService.java](../src/main/java/com/example/agent/application/ConversationService.java:535)。

`getEffectiveMessages()` 会：

- 取得当前会话已有消息；
- 加入上下文容量告警；
- 过滤已经标记为 `memorySaved` 的消息；
- 返回本次真正送给模型的消息列表。

最后调用：

```java
llmClient.chatStream(messages, tools, streamCallback);
```

见 [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:256)。

因此它不是只传：

```text
user: 我叫什么？
```

而是传：

```text
system + 之前多轮消息 + 工具结果 + 当前用户消息
```

## 7. 模型回答如何保存

模型流式回答时，文本片段先通过 SSE 发给前端：

```java
sseWriter.sendSseEvent("content", ...);
```

流式响应结束后，把完整 assistant 消息添加到会话：

```java
conversationService.addAssistantMessage(
    conversation,
    assistantMessage,
    response.getUsage()
);
```

见 [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:434)。

`addAssistantMessage()` 最终仍然进入统一的 `addMessage()`，所以会同时：

- 加入 `Conversation`；
- 写入 `conversation.jsonl`；
- 保存 Token usage；
- 触发记忆处理。

这样下一次用户请求进来时，这条回答已经属于历史上下文。

## 8. 一次用户请求内部还有 Agent 多轮

这里有两层“多轮”。

第一层是用户对话多轮：

```text
POST /api/chat 第一次
POST /api/chat 第二次
POST /api/chat 第三次
```

第二层是一次请求内部的工具调用循环：

```text
用户消息
  ↓
LLM 决定调用 read_file
  ↓
执行 read_file
  ↓
把 tool result 加入 Conversation
  ↓
再次调用 LLM
  ↓
LLM 决定调用 edit_file
  ↓
执行 edit_file
  ↓
再次调用 LLM
  ↓
LLM 输出最终回答
```

这个内部循环在：

```java
for (int turn = 0; turn < MAX_TURNS; turn++)
```

最多执行 50 轮。[WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:210)

每次工具执行完成后，工具结果也会写入同一个 `Conversation`。然后下一次循环重新调用：

```java
getContextForInference(conversation)
```

所以模型能够看到刚才的工具结果。

## 9. 应用重启后如何恢复同一会话

内存中的 `sessions` 在进程退出后会丢失，因此项目把消息持久化为：

```text
.hippo/
└── sessions/
    └── 2026-08-27/
        └── web-1787800000000/
            ├── conversation.jsonl
            ├── session.json
            ├── system-prompt.txt
            └── memory/
                └── session-memory.md
```

消息文件路径定义在 [WorkspaceManager.java](../src/main/java/com/example/agent/logging/WorkspaceManager.java:103)。

重启后再次发送相同 `sessionId`：

1. `sessions` 内存缓存找不到；
2. 创建新的 `Conversation` 对象；
3. 从 `system-prompt.txt` 恢复原来的系统提示词；
4. 用 `TranscriptLoader` 加载 `conversation.jsonl`；
5. 将历史消息重新装进 `Conversation`；
6. 继续本轮请求。

恢复入口是：

```java
conversationService.resumeConversation(conversation, id);
```

见 [WebSessionManager.java](../src/main/java/com/example/agent/web/session/WebSessionManager.java:318)。

普通会话完整恢复：

```java
conversation.clear();
conversation.addMessage(Message.system(systemPrompt));
conversation.addMessages(allMessages);
```

见 [ConversationService.java](../src/main/java/com/example/agent/application/ConversationService.java:672)。

如果会话很长，并且存在 `session-memory.md`，恢复时会使用：

```text
system prompt
+ 早期会话摘要
+ 最近完整消息
```

避免把全部超长历史重新装入上下文。

## 10. 前端消息缓存不等于模型上下文

前端也会把历史消息按 `sessionId` 缓存到 `localStorage`，但它主要用于：

- 切换会话时快速显示；
- 页面刷新后立即渲染；
- 避免界面先出现空白。

真正决定模型上下文的是后端：

```text
Conversation + conversation.jsonl
```

而不是前端的消息缓存。

后端的历史消息查询接口：

```http
GET /api/sessions/{sessionId}/messages
```

也直接从 JSONL 读取。[SessionApiHandler.java](../src/main/java/com/example/agent/web/handler/SessionApiHandler.java:117)

## 11. 同一会话的并发控制

前端先检查：

```typescript
if (sess?.isSending) return false;
```

防止同一个页面在回答尚未结束时再次发送。[chatStore.ts](../frontend/src/stores/chatStore.ts:618)

后端还使用：

```java
Map<String, ReentrantLock> sessionLocks
```

相同 `sessionId` 共用同一把锁，不同会话可以并行：

```text
session-A 请求1 ──┐
                  ├── 串行
session-A 请求2 ──┘

session-B 请求1 ───── 可与 session-A 并行
```

不过这里存在一个潜在问题：等待锁超过 30 秒后，代码会删除旧锁并新建一把锁。如果原请求仍持有旧锁，后来的请求可能进入新锁，造成两个线程同时修改同一个 `Conversation`。[WebSessionManager.java](../src/main/java/com/example/agent/web/session/WebSessionManager.java:190)

更安全的处理应该是：锁等待超时后直接向第二个请求返回“会话正在运行”，而不是替换锁对象。

总结成一句调用链：

```text
相同 sessionId
→ 找到相同 Conversation
→ 追加本轮 user 消息
→ 取出完整有效历史
→ 调用 LLM
→ 追加 assistant/tool 消息
→ 写入 JSONL
→ 下一轮继续复用
```
