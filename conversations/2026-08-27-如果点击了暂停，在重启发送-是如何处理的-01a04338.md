# 如果点击了暂停，在重启发送 是如何处理的

- 会话 ID：`01a04338-04c4-74e1-b899-9780feb7ea1e`
- 导出来源：Codex Desktop（仅保留对话内容）

## 用户

如果点击了暂停，在重启发送 是如何处理的

## Codex（过程说明）

我先沿着“暂停 → 重启发送”的调用链检查状态保存、队列恢复和重复发送保护，再结合代码说明实际处理方式。

## Codex（过程说明）

目前界面代码里的“暂停”实际对应“停止生成/中断”，不是可原地续流的 pause。我继续核对重新发送时，上一轮的半截回复和会话历史如何进入下一次请求。

## Codex（最终回答）

当前实现中，“暂停”本质上是“停止生成”，重新发送也不是断点续传，而是发起一个全新的模型请求。

具体流程：

1. 点击停止生成

   - 前端中断 SSE 请求。
   - 向后端发送会话级取消信号。
   - 已经显示的半截回复会暂时保留在前端界面。
   - 后端停止 LLM/Agent 后续循环，但已经执行完成的工具操作或文件修改不会自动回滚。

   相关代码：[chatStore.ts](../frontend/src/stores/chatStore.ts:704)、[ToolAbortHandler.java](../src/main/java/com/example/agent/web/handler/ToolAbortHandler.java:38)

2. 再次点击“重试”

   目前只是把原来的用户消息再次调用 `send(content)`，不会删除上一轮，也不会从中断位置继续：

   [ChatPanel.tsx](../frontend/src/components/chat-panel/ChatPanel.tsx:504)

   后端会：

   - 等上一轮释放会话锁；
   - 清除旧的取消标记；
   - 把重试内容作为一条新的用户消息写入；
   - 使用当前完整会话上下文重新请求模型。

   [ChatApiHandler.java](../src/main/java/com/example/agent/web/handler/ChatApiHandler.java:190)

3. 当前实现需要注意的问题

   停止时，半截 AI 回复通常只保留在前端，没有写入后端会话，因为后端在取消检查处直接返回，尚未执行 assistant 消息落库：

   [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:354)  
   [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:434)

   因此点击“重试”后，后端上下文可能变成：

   ```text
   user: 原问题
   user: 原问题（重试再次写入）
   ```

   并不是替换原问题。这意味着当前“重试”更准确地说是“重复发送”。

如果是关闭并重启应用后再发送，恢复逻辑会发现会话最后一条是用户消息，并插入“之前的回复被中断，请继续”的恢复提示，然后处理新消息：[ConversationService.java](../src/main/java/com/example/agent/application/ConversationService.java:736)。

## 用户

这里的实现原理是什么

## Codex（最终回答）

核心原理是：前端负责立即停止显示，后端通过“协作式取消标记”停止 Agent，重新发送则创建一个新回合；磁盘 Transcript 负责应用重启后的恢复。

```text
点击停止
   │
   ├─ 前端 AbortController 中断 SSE
   ├─ POST /api/tool/abort 设置会话取消标记
   └─ 前端保存当前已显示的半截内容
              │
              ▼
后端 LLM/Agent 在检查点发现取消
   └─ 停止模型读取、跳过后续工具和循环
              │
              ▼
重新发送
   ├─ 等上一轮释放会话锁
   ├─ 清除旧取消标记
   ├─ 写入一条新的 user 消息
   └─ 基于当前会话上下文重新调用模型
```

### 1. 为什么要同时中断 SSE 和通知后端

前端执行两种中断：

```ts
activeStreamControllers.get(sid)?.abort();
chatApi.abortTool({ sessionId: sid });
```

见 [chatStore.ts](../frontend/src/stores/chatStore.ts:704)。

两者作用不同：

- `AbortController.abort()`：立即断开前端正在读取的 SSE，让按钮和界面马上恢复。
- `/api/tool/abort`：通知后端真正停止模型调用，避免前端虽然断开了，但后端仍然消耗 Token、执行工具。

这是“数据通道 + 控制通道”的设计。单纯依赖 SSE 断开不可靠，因为后端可能要等到下一次写数据时才发现 TCP 已关闭。

### 2. 后端如何停止正在执行的 Agent

后端不会粗暴终止线程，而是给对应会话设置一个线程安全的取消标记：

```java
cancelManager.cancel(sessionId);
```

见 [ToolAbortHandler.java](../src/main/java/com/example/agent/web/handler/ToolAbortHandler.java:38)。

Agent 在多个检查点读取这个标记：

- 调用模型前；
- 接收流式 Token 时；
- 模型调用返回后；
- 执行工具前；
- 进入下一轮 Agent 循环前。

见 [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:211)。

流式读取过程中检测到取消，还会调用：

```java
llmClient.abortCurrentRequest();
```

这属于“协作式取消”：各执行阶段主动检查取消状态并安全退出，避免直接杀线程造成锁未释放、Transcript 未刷盘等问题。

### 3. 半截回复为什么还能显示

前端收到的 Token 会先进入当前会话的流式缓冲区。停止时执行：

```ts
commitStreamingMessage(sid);
```

见 [chatStore.ts](../frontend/src/stores/chatStore.ts:716)。

它把已经收到的内容转成一条本地 assistant 消息，所以界面上不会立刻丢失半截回答。

但后端只有在模型回合正常处理完成后才执行：

```java
addAssistantMessage(conversation, assistantMessage, usage);
```

见 [WebAgentOrchestrator.java](../src/main/java/com/example/agent/web/orchestrator/WebAgentOrchestrator.java:434)。

因此，停止发生在模型流式输出阶段时：

- 用户消息：已经写入后端 Transcript；
- 半截 AI 回复：通常只存在于前端内存；
- 已经完成的工具或文件操作：可能已经真实生效，不会因停止而自动回滚。

这也是刷新页面后半截回复可能消失的原因。

### 4. 重新发送为什么不会被旧取消状态影响

每个会话有独立锁。新请求需要等待上一轮结束并释放锁，然后后端清除该会话残留的取消标记：

```java
SessionCancelManager.getInstance().reset(sessionId);
```

见 [ChatApiHandler.java](../src/main/java/com/example/agent/web/handler/ChatApiHandler.java:190)。

所以取消标记只影响上一轮，不会导致下一轮刚开始就被取消。

### 5. “重试”实际上是怎样处理的

当前重试按钮只是把原用户消息再发送一次：

```ts
void send(content);
```

见 [ChatPanel.tsx](../frontend/src/components/chat-panel/ChatPanel.tsx:504)。

它没有执行：

- 删除半截回答；
- 截断上一轮历史；
- 回滚工具产生的文件修改；
- 从原来的 Token 位置断点续传。

所以其语义是“追加一个新回合”，可能形成：

```text
user: 实现登录功能
user: 实现登录功能    ← 点击重试后再次追加
assistant: 重新生成的完整回答
```

如果希望实现真正的“重新生成”，通常应先把会话截断到原用户消息之前，再重新写入该消息并发起请求。

### 6. 应用重启后的恢复原理

应用重启后，前端内存中的半截回复已经不存在。后端以磁盘上的 JSONL Transcript 为准恢复会话。

如果 Transcript 最后一条是用户消息，说明回复可能在中途被停止，恢复逻辑会补一条内部提示：

```text
[会话恢复提示] 之前的回复被中断，请继续。
```

见 [ConversationService.java](../src/main/java/com/example/agent/application/ConversationService.java:736)。

因此整体采用的是：

- 前端流式缓冲保证停止时界面响应迅速；
- 后端取消标记保证计算真正停止；
- 会话锁保证同一会话不会并发执行两个回合；
- Transcript 保证崩溃或应用重启后能够恢复；
- 恢复修复逻辑负责处理不完整的消息结构。
