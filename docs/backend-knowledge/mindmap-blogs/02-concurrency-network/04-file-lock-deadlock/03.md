# case sensitivity：底层原理、源码与实现

> 所属专题：[多文件锁与死锁](../../../02-concurrency-network/04-file-lock-deadlock.md)  
> 导图路径：资源身份 → case sensitivity  
> 类型：资源身份规范化节点；编号 3/12

## 1. 学习结论

“case sensitivity”是资源身份规范化节点。掌握标准是能从线程/状态/协议层说明正常路径、竞争路径、超时路径和关闭路径。

## 2. 概念与项目语境

死锁需要同时满足互斥、持有并等待、不可抢占、循环等待。多文件编辑无法消除前三个条件，通常通过全局锁顺序消除第四个条件：所有任务先把路径变成同一种 canonical identity，再按稳定字典序获取，释放时逆序。

排序之前必须完成身份统一。`a/../b.txt`、大小写差异、符号链接和 Windows 盘符可能指向同一文件；若它们生成不同 lock key，Java 锁保护的只是字符串而不是底层文件。进程内 `ReentrantLock` 也不约束编辑器、Git 或另一个 HippoBuddy 进程，因此执行写入前仍需版本/内容 hash 校验。

## 3. 底层实现原理

不同路径表示先归一为同一 canonical identity，再用于权限判断、锁键和版本比较。

分析任何并发实现都要写出：共享状态由谁拥有；哪些操作必须原子；可见性由锁、volatile、原子类还是队列保证；容量耗尽如何传播；取消后谁负责释放实际资源。

## 4. HippoBuddy 源码追踪

- [FileLockManager.java](../../../../../src/main/java/com/example/agent/tools/concurrent/FileLockManager.java)

```java
for (String p : filePaths) {
    String n = normalizePath(p);
    if (!normalized.contains(n)) normalized.add(n);
}
normalized.sort(String::compareTo);

try {
    for (String n : normalized) {
        ReentrantLock lock = fileLocks.computeIfAbsent(n, k -> new ReentrantLock());
        lock.lock();
        acquired.add(lock);
    }
    return action.run();
} finally {
    for (int i = acquired.size() - 1; i >= 0; i--) acquired.get(i).unlock();
}
```

围绕“case sensitivity”追踪创建、进入临界区/协议帧、状态提交、异常转换和 finally 释放位置。

## 5. 为什么这样实现

否则同一文件可能获得多把锁，或符号链接/大小写差异绕过边界。

若省略该节点，问题通常不会在单线程 happy path 暴露，而会在高并发、慢下游、客户端断开或关闭阶段表现为乱序、泄漏、死锁或假成功。

## 6. 完整代码实现

以下机制代码已通过 Java 21 编译检查：

```java
import java.nio.file.*;
import java.time.*;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.locks.ReentrantLock;

public final class OrderedFileLocks {
    private final ConcurrentHashMap<Path, ReentrantLock> locks = new ConcurrentHashMap<>();

    <T> T withLocks(Collection<Path> input, Duration timeout, Callable<T> action) throws Exception {
        List<Path> keys = input.stream().map(p -> p.toAbsolutePath().normalize()).distinct()
                .sorted(Comparator.comparing(Path::toString)).toList();
        List<ReentrantLock> acquired = new ArrayList<>();
        long deadline = System.nanoTime() + timeout.toNanos();
        try {
            for (Path key : keys) {
                ReentrantLock lock = locks.computeIfAbsent(key, ignored -> new ReentrantLock());
                long remaining = deadline - System.nanoTime();
                if (remaining <= 0 || !lock.tryLock(remaining, TimeUnit.NANOSECONDS))
                    throw new TimeoutException("cannot lock " + key);
                acquired.add(lock);
            }
            return action.call();                       // 锁内必须重新校验文件版本
        } finally {
            for (int i = acquired.size() - 1; i >= 0; i--) acquired.get(i).unlock();
        }
    }
}
```

把与“case sensitivity”有关的保护删除或移位，再用 latch/barrier、短 deadline 或强制异常稳定复现失败，不要只用 sleep 猜测时序。

## 7. 疑难点与失败推演

- 线程安全容器不保证跨多步业务不变量；
- timeout 只停止等待，不自动取消底层 I/O；
- 虚拟线程降低线程成本，不提供下游背压；
- 成功事件、状态提交和资源释放的顺序必须能经受中途崩溃。
